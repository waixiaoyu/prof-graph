# M2 — 学术传承 + 项目合作

> **阶段**：Specify（spec.md）⏳ 草案待评审（2026-08-26）
> **状态**：草案
> **上游**：M1 已完成（2026-08-26）；constitution 第一阶段范围含本里程碑两种直接关系

---

## 1. 背景与目标

M1 打通了"论文合作"全链路（arXiv → GLM 抽取 → 消歧 → 关系入库 → 图谱展示）。M2 补全第一阶段另外 **2 种直接关系**及其数据源，跑通完整的第一阶段直接关系网络：

| 关系 | 数据源 | 链路 |
|------|--------|------|
| **学术传承** `academic_mentorship` | 高校官网定向爬取（教师主页 / 实验室成员页 / 毕业生名单页） | 种子配置 → 定向爬虫 → GLM 抽取 → 中文消歧 → 关系入库 |
| **项目合作** `project_cooperation` | AI 媒体 RSS 资讯（机器之心 / 新智元 / 量子位等，按可获得性） | RSS 订阅 → GLM 抽取 → 消歧 → 关系入库 |

两条链路**复用 M1 已建成的全部基础设施**：failed_jobs 重试、token 熔断、消歧审核队列、证据链机制、图谱/筛选前端。同时落实 M1 遗留的 Person 字段扩展（职位/主页，RD-8 曾明确推迟到本里程碑）。

**成功标志**：图谱中能同时看到三种直接关系（论文合作实线 + 学术传承 + 项目合作，视觉可区分），任意一条关系都能点开看到网页/资讯证据原文链接。

**范围口径**：延续 M1 RD-13——高校官网（国内高校）与国内 AI 媒体天然在中国学者范围内；资讯/网页中出现的外国学者及其机构，按 M1 口径作为"相关外国学者"保留，纯外国场景不建关系。

## 2. 用户故事

### US-1：查看学术传承网络
> 作为技术合作经理，我希望选择某高校/实验室后，能看到其师生、同门之间的学术传承网络，以便判断这个团队的人脉纵深和传承脉络。

### US-2：查看项目合作网络
> 作为技术合作经理，我希望看到资讯报道过的项目合作网络（谁和谁共同参与了什么项目），以便了解产学合作圈。

### US-3：追溯传承/项目关系证据
> 作为技术合作经理，我希望点击任意一条学术传承或项目合作关系，能打开支撑它的网页快照或资讯原文链接，以验证关系可靠性。

### US-4：查看学者完整档案
> 作为科研管理人员，我希望在学者详情中看到其职位/职称和个人主页（来自教师主页），以便评估和联系。

### US-5：维护数据源配置
> 作为管理员，我希望通过配置文件维护高校爬取种子（学校/院系/实验室/教师主页 URL）和 RSS 源清单，以便控制采集范围。

## 3. 功能需求（EARS）

> 标注：`[Ubiquitous]` 始终 / `[WHEN]` 事件驱动 / `[IF]` 异常处理

### FR-1 AI 媒体 RSS 资讯采集（项目合作数据源）

- **FR-1.1** `[Ubiquitous]` 系统应每日定时（APScheduler）拉取配置文件中启用的 AI 媒体 RSS 源；源清单（名称、URL、启用开关）配置驱动，管理员改文件即可增删。
- **FR-1.2** `[IF]` 同一条资讯（link/guid 相同）被重复拉取，系统应跳过，不得重复入库。
- **FR-1.3** `[Ubiquitous]` 每条入库资讯应记录：标题、摘要、原文链接、发布时间、来源媒体、原始条目（审计用）。
- **FR-1.4** `[Ubiquitous]` 采集后系统应对资讯做**信号预筛**：不含人员/项目参与信号的资讯（无具体人名、无项目/合作事件的泛科普内容）不进入 GLM 抽取管线，仅留档。预筛方式（规则/GLM）在 plan 定。
- **FR-1.5** `[IF]` RSS 请求失败（超时、HTTP 错误、源不可用），系统应记录到 failed_jobs，不中断整批其他源的抓取。
- **FR-1.6** `[WHEN]` 管理员在后台触发"立即更新"时，系统应支持单独触发资讯抓取并返回进度（复用 M1 批次进度机制）。

### FR-2 高校官网定向爬取（学术传承数据源）

- **FR-2.1** `[Ubiquitous]` 系统应按配置文件中的**种子清单**定向爬取：每条种子含学校、院系/实验室、入口 URL、页面类型（教师主页/实验室成员页/毕业生名单页）。首批种子范围见 OQ-1。
- **FR-2.2** `[Ubiquitous]` 爬取应为**封闭定向**：仅抓取种子入口页及其指向的成员/列表子页（深度受限，配置项），不做开放爬行、不自动发现种子外的新页面。
- **FR-2.3** `[Ubiquitous]` 每个抓取页面应保存快照记录：URL、标题、抓取时间、正文文本、来源种子标识、内容指纹（hash）。
- **FR-2.4** `[Ubiquitous]` 系统应按配置周期重爬种子页面；`[IF]` 页面内容指纹未变化，应跳过重新抽取。
- **FR-2.5** `[IF]` 页面抓取失败（超时、HTTP 错误、结构变化解析失败），系统应记录到 failed_jobs，不中断其他种子的抓取。
- **FR-2.6** `[WHEN]` 管理员触发"立即更新"时，系统应支持单独触发爬取并返回进度。

### FR-3 GLM 抽取（资讯 + 网页）

- **FR-3.1** `[Ubiquitous]` 对通过预筛的资讯，系统应调用 GLM 抽取：涉及的人员（姓名、机构、角色）、项目参与事实（何人参与何项目、角色、时间）、项目信息（名称、类型、时间范围）。项目信息的建模方式见 OQ-4。
- **FR-3.2** `[Ubiquitous]` 对每个新抓取/内容变化的页面，系统应调用 GLM 抽取：成员名单（姓名、身份：教授/副研究员/博士生/硕士生等）、师生关系信号（谁是谁的导师）、分组信号（同实验室/同导师/同届）。
- **FR-3.3** `[Ubiquitous]` GLM 输出结构化 JSON，schema 在 plan.md 定义；沿用 M1 RD-11 部分容错原则（能解析的入库，整篇失败才重试）。
- **FR-3.4** `[Ubiquitous]` GLM 调用失败重试（1/5/25min 退避 → 死信）与 token 熔断**复用 M1 机制**，资讯/网页抽取用量计入同一预算体系。
- **FR-3.5** `[Ubiquitous]` 对教师主页类型的页面，系统应顺带抽取 Person 扩展字段：职位/职称、个人主页 URL、电子邮箱（RD-8 遗留项落地）。抽取不到的字段留空，不猜。
- **FR-3.6** `[IF]` 抽取结果中无任何人员/关系信号，系统应标记该资讯/页面为已处理-无信号，不建实体关系。

### FR-4 中文人名消歧与实体衔接

- **FR-4.1** `[Ubiquitous]` 系统应支持中文姓名与英文/拼音姓名的归一互匹配（如"张三" ↔ "Zhang San"），归一规则（拼音转换、中英姓名结构差异）在 plan 定。
- **FR-4.2** `[Ubiquitous]` 资讯/网页中抽取的新人员应与已有 Person 消歧归并，复用 M1 框架：强键优先（openalex_id 不适用于中文名场景，以"姓名归一 + 机构"为强信号）、5 因素加权打分、≥0.8 自动归并 / 0.5–0.8 入审核队列 / <0.5 新建。
- **FR-4.3** `[Ubiquitous]` 网页抽取的机构归属应支持高校/院系/实验室三级粒度入库（供 FR-5.3 同机构加分信号使用）。
- **FR-4.4** `[IF]` 教师主页上的"张三"与论文作者"Zhang San"匹配得分落入 0.5–0.8，应进入现有消歧审核队列，管理员合并后其论文合作与学术传承关系归到同一 Person。

### FR-5 学术传承关系建立

- **FR-5.1** `[Ubiquitous]` 系统应建立 `academic_mentorship` 关系（人↔人），并记录**子类型**属性：师生 `mentor_student`、同实验室 `same_lab`、同导师 `same_advisor`、同届毕业 `same_cohort`。子类型清单以 review 确认为准（见 OQ-2）。
- **FR-5.2** `[Ubiquitous]` 每条关系应计算置信度：`0.4×数据源可信度 + 0.3×关系推断确定性 + 0.2×信息明确性 + 0.1×时间吻合度`（各维度分档取值在 plan 定，参照 docs/04 既有设计）。
- **FR-5.3** `[Ubiquitous]` 两人存在同机构背景时，应按粒度对置信度加分（上限 1.0）：同组/实验室 +0.10、同系 +0.05、同院 +0.03、同校 +0.01。同机构本身不建关系（constitution 原则 5）。
- **FR-5.4** `[Ubiquitous]` 每条关系应关联证据：支撑它的页面快照（或资讯，若 OQ-3 确认论文致谢纳入则为论文）。证据须可跳转原文链接。
- **FR-5.5** `[IF]` 同一对人、同一子类型的关系再次被发现（如重爬页面、多页面覆盖），系统应合并证据、按证据质量重算置信度，不得新建重复关系。
- **FR-5.6** `[Ubiquitous]` 关系应记录时间范围（在校/在读时间）、角色描述（如"导师-博士生"）、证据描述（人类可读）。

### FR-6 项目合作关系建立

- **FR-6.1** `[Ubiquitous]` 对同一项目中抽取到的任意两位参与者 A、B，系统应建立一条 `project_cooperation` 关系（人↔人）。
- **FR-6.2** `[Ubiquitous]` 每条关系应计算置信度：`0.3×信息明确性 + 0.3×信息充分性 + 0.2×数据源可信度 + 0.2×可访问性`（分档取值 plan 定）。
- **FR-6.3** `[Ubiquitous]` 每条关系应关联证据：支撑它的资讯（含项目名称、报道链接）。
- **FR-6.4** `[IF]` A、B 已存在 `project_cooperation` 关系（来自其他项目/资讯），系统应合并证据、更新时间范围、按共同项目数重算强度，不得新建重复关系。
- **FR-6.5** `[Ubiquitous]` 三种关系类型统一沿用 M1"身份置信度 + 关系强度"双层模型（RD-10 延续）；传承/项目两类关系的强度语义与"次数"定义（证据条数/共同项目数）在 plan 定。设计原则：官方列表类证据一次即可达高强度，致谢类弱证据保持中低强度。

### FR-7 图谱可视化与前端整合

- **FR-7.1** `[Ubiquitous]` 图谱主页应同时展示三种关系类型，视觉可区分（线型/颜色区分；M1 实线=论文合作，传承与项目的编码方案 plan/前端定）。
- **FR-7.2** `[Ubiquitous]` 系统应提供关系类型筛选器（按类型显示/隐藏，可多选），与 M1 既有筛选（方向/赛道/强度/合作次数）叠加生效。
- **FR-7.3** `[WHEN]` 用户点击学术传承或项目合作关系时，系统应展示证据链（页面快照标题+链接 / 资讯标题+来源+链接），链接可打开原文。
- **FR-7.4** `[WHEN]` 用户查看学者详情时，系统应展示新增的职位/职称、个人主页字段（有则显示）。
- **FR-7.5** `[Ubiquitous]` M1 既有功能（搜索、筛选、复核队列、后台仪表盘）应无回归；仪表盘应纳入资讯/爬取任务的状态与失败记录。

## 4. 非功能需求

- **NFR-1 爬虫合规**：遵守目标站点 robots.txt；请求间隔默认 ≥2 秒（可配置）；UA 明确标识本系统；不登录、不绕过反爬、不抓非公开内容；单站点失败不重试风暴（复用退避机制）。
- **NFR-2 成本**：资讯/网页抽取 token 用量计入 M1 既有日/周双预算熔断；新增常规用量估算与预算校准在 plan 完成。
- **NFR-3 可观测**：后台仪表盘可见 RSS 源状态、爬取种子状态（成功/失败/跳过）、新增 token 用量。
- **NFR-4 性能**：三种关系并存后，图谱渲染仍满足 M1 NFR-1 口径（单视图 1000 节点）。
- **NFR-5 数据不变量**：M1 已建立的六项不变量巡检应扩展覆盖新关系类型（关系唯一性、证据非空、置信度域等），双跑幂等要求同样适用于新链路。

## 6. 验收标准（Acceptance Criteria）

> 满足以下全部条件，M2 视为完成。数量阈值以"配置种子后运行 3-7 天或手动触发"为口径（类比 M1 AC-1）。

- **AC-1**：配置 ≥2 所高校的种子后，系统能定向爬取教师主页/实验室成员页并保存页面快照 ≥20 条，含内容指纹。
- **AC-2**：图谱中能查看到 ≥10 条学术传承关系（含子类型、置信度、时间范围），每条可打开 ≥1 条页面证据原文链接。
- **AC-3**：≥1 个 RSS 源正常拉取入库；在含项目信号的资讯上产生 ≥3 条项目合作关系，每条可打开资讯证据原文链接。
- **AC-4**：图谱页三种关系类型视觉可区分，类型筛选器生效（隐藏某类型后对应边消失）。
- **AC-5**：构造中英文同一人场景（教师主页"张三" vs 论文作者"Zhang San"），消歧后合并为同一 Person，两类关系（若有）挂到同一人。
- **AC-6**：学者详情显示来自教师主页的职位/主页字段（有数据时）。
- **AC-7**：爬取限速与 robots.txt 遵守可通过配置和日志验证（无短间隔请求记录；被 robots 禁止的路径未抓取）。
- **AC-8**：模拟资讯抓取失败与 GLM 抽取失败，failed_jobs 有记录并按 1/5/25min 退避重试。
- **AC-9**：同一实验室页面重爬（内容不变）不产生重复关系、不重复调用 GLM；内容变化后重抽取且关系合并不重复。
- **AC-10**：数据不变量巡检扩展到三种关系类型并通过；全管线（含新链路）双跑幂等测试通过。

## 7. 已确认决策（Resolved Decisions）

> 本节为**提案**（标注 *(提案)*），review 时逐条确认或推翻；确认后去掉标记固化。

- **RD-M2-1（关系类型扩展方式）** *(提案)*：三种直接关系共存于 `relationships` 表，`type` 扩展取值 `academic_mentorship` / `project_cooperation`；证据表扩展方案（泛化证据 vs 分类型证据表）留 plan 决定，spec 只约束"证据可追溯、可跳原文"。
- **RD-M2-2（置信度公式采纳）** *(提案)*：采纳 docs/04 已设计的两类公式（FR-5.2 / FR-6.2）及学术传承同机构加分（FR-5.3），各维度分档数值在 plan 落定。
- **RD-M2-3（身份置信度/强度双层模型延续）** *(提案)*：新关系类型沿用 RD-10 双层模型，字段语义与各类型强度算法在 plan 定（FR-6.5 原则）。
- **RD-M2-4（Person 字段扩展落地）** *(提案)*：本里程碑落地职位/职称、个人主页、邮箱三字段（RD-8 遗留），仅来自教师主页抽取，缺失留空不猜。
- **RD-M2-5（爬取封闭性）** *(提案)*：高校官网爬取严格限定在种子清单 + 受限深度内，不做开放发现（out-of-scope 对应）。
- **RD-M2-6（基础设施复用）** *(提案)*：failed_jobs / token 熔断 / 消歧队列 / 批次进度 / 后台仪表盘全部复用 M1 实现，扩展而非重建。

## 8. 开放问题（Open Questions）

> review 时逐条决议，结论固化为 RD 并回填正文。

- **OQ-1（高校种子首批范围）**：首批爬哪些学校/院系/实验室？（建议：2-3 所目标高校的 CS/EE 相关院系 + 其重点实验室，种子清单由用户提供或 review 时指定；配置驱动，后续可扩。）
- **OQ-2（学术传承子类型清单）**：FR-5.1 提出的 4 个子类型（师生/同实验室/同导师/同届）是否够用？"实习指导"（docs/01 已并入传承）是否需要单独子类型？
- **OQ-3（论文致谢是否纳入）**：docs 列"论文致谢"为传承数据源之一；M1 已有 arXiv 全文获取能力，可复用抽取 pass。纳入则多一条证据来源（数据源可信度低档 0.6）；不纳入则传承仅靠高校官网。（建议：纳入，作为二级来源，实现成本低。）
