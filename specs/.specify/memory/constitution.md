# Project Constitution

> 项目级硬约束。每一个 spec、plan、task 和 agent 动作都必须遵守。任何与本文件冲突的下游产物视为无效，需修正。

最后更新：2026-08-31（§3.1 修订：spatiotemporal 移出待数据复盘）

---

## 1. 项目身份

- **项目名**：企业级学术网络治理系统（prof-graph）
- **定位**：基于公开信息的学术人脉网络自动发现与治理系统
- **应用场景聚焦**：校企合作、产学研合作、人才引进
- **部署形态**：单机本地部署的内部系统，管理员使用（非多租户、非公网）

## 2. 技术栈（不可漂移）

| 组件 | 选型 |
|------|------|
| 数据库 | PostgreSQL 14+ |
| 后端 | FastAPI（Python 3.10+） |
| 前端 | React（Node.js 18+） |
| 图谱可视化 | React Flow 或 Cytoscape.js |
| LLM | GLM-5.2（Anthropic 协议接入） |
| 任务调度 | **APScheduler**（应用内调度，禁用 Celery / 系统 cron） |

> 选型变更必须先改本文件并经人工确认，不得在 task 实现阶段偷换。

## 3. 第一阶段范围边界（硬边界）

### 3.1 第一阶段包含

- **3 类数据源**：arXiv RSS、AI 媒体 RSS（机器之心/新智元/量子位等，按可获得性）、高校官网爬取（特例）
- **3 种直接关系**（均为人↔人）：
  - 论文合作 `paper_cooperation`
  - 项目合作 `project_cooperation`
  - 学术传承 `academic_mentorship`
- **2 种潜在关系发现方法**（均为人↔人）：
  - `common_network`、`research_similarity`
  - （2026-08-31 修订：`spatiotemporal` 移出——现有数据无任职区间与机构粒度支撑，探针实证见 specs/M3 spec §7；数据成熟后经人工确认可回归）
- 证据链追溯、实体消歧、关系去重、图谱可视化、搜索、后台编辑

### 3.2 第一阶段明确排除（out of scope）

- ❌ 顾问关系（人↔机构，无企业数据源）
- ❌ role_match（人↔企业潜在关系，无企业数据源）
- ❌ 企业实体、企业数据源、校企合作挖掘
- ❌ 商业科技媒体爬取（36氪/虎嗅/钛媒体/企业官网）
- ❌ 智能推荐系统、AI 问答
- ❌ 多用户、权限体系、公网部署

> **措辞约定**：RSS = 第一阶段；网页爬虫 = 第二阶段。唯一例外是**高校官网爬取**（学术传承关系的唯一可靠数据源），特例纳入第一阶段。

## 4. 核心设计原则（不可违反）

1. **以人为中心**：Person 是中心实体，其他实体围绕展开。
2. **证据先于关系**：先有证据 → 识别关系 → 关联证据。无证据的关系不存储。
3. **关系即实体**：关系有独立的属性和证据链，可追溯"为什么"。
4. **`relationships` 表只存人↔人**：人↔机构关系（如顾问）留到第二阶段扩展表结构。
5. **同机构关系不是独立关系类型**：是学术传承关系和潜在关系 spatiotemporal 的辅助推断信号，强度随粒度递减：同组 > 同系 > 同院 > 同校。

## 5. SDD 工作流约束（本项目的元规则）

1. **spec 是唯一事实来源**：当代码与 spec 冲突时，以 spec 为准；当需求变化时，先改 spec 再改代码。
2. **四阶段顺序，每阶段人工 review**：spec.md → plan.md → tasks.md → implement。任何阶段未经人工确认不得进入下一阶段。
3. **一个里程碑 = 一个 spec 目录**：`specs/M{N}-{name}/{spec.md, plan.md, tasks.md}`。
4. **EARS 语法写需求**：可测试、无歧义。
5. **spec 要短（1-3 页）**：大了就拆。
6. **每个 spec 必须写 out-of-scope 和验收标准**。
7. **agent 在 implement 阶段是"快速初级工程师"**：被 spec 约束，不得自由发挥；每完成一个 task 跑测试、按逻辑块提交。
