# M1 — 论文合作全链路

> **阶段**：Specify（spec.md）✅ 已确认（2026-08-19，含 RD-1~RD-12；2026-08-31 补充 RD-13）
> **状态**：定稿
> **最后更新**：2026-08-31

---

## 1. 背景与目标

M1 是整个系统的第一个里程碑，目标是跑通**最小可验收闭环**：从 arXiv 拿到论文 → GLM 抽取作者和机构 → 建立"论文合作"关系 → 在图谱里能看到。

本里程碑**只做论文合作这一种关系**，目的是把"数据采集 → GLM 抽取 → 入库 → 展示"的主干道打通；其他 2 种直接关系（学术传承、项目合作）留给 M2。

**数据范围（RD-13，2026-08-31 补充）**：本里程碑只治理**含有中国学者**的论文（含中国学者在国外机构任职的情形）；这些论文上的外国合作者及其机构作为"相关外国机构/学者"一并保留。纯外国论文不进关系网络。

**成功标志**：能在图谱里看到某个 AI 领域（如 transformer）的论文合作网络，每条合作关系都能点开看到证据论文。

## 2. 用户故事

### US-1：查看论文合作网络
> 作为技术合作经理，我希望从预设的业务方向/学术赛道筛选器中选择一个方向（如 ADN、network automation），看到该方向内学者之间的论文合作网络，以便快速了解这个圈子的人脉结构。

### US-2：追溯合作关系证据
> 作为技术合作经理，我希望点击任意一条合作关系，能看到支撑它的具体论文（标题、年份、会议），以便验证这条关系的可靠性。

### US-3：搜索学者
> 作为科研管理人员，我希望按姓名或机构搜索某位学者，在图谱中定位到他及其合作关系。

### US-4：查看学者详情
> 作为科研管理人员，我希望点击某位学者节点，看到他的机构、研究方向、发表的论文列表。

### US-5：手动触发数据更新
> 作为管理员，我希望在后台点击"立即更新"，实时看到 arXiv 抓取和 GLM 抽取的进度，以便在不等定时任务的情况下刷新数据。

## 3. 功能需求（EARS）

> 标注：`[Ubiquitous]` 始终 / `[WHEN]` 事件驱动 / `[WHILE]` 状态驱动 / `[IF]` 异常处理 / `[WHERE]` 可选特性

### FR-1 数据采集与过滤（arXiv RSS）

- **FR-1.1** `[Ubiquitous]` 系统应每日（由 APScheduler 调度，具体时间在 plan 定）从 arXiv RSS 拉取 **18 个分类**的新论文：cs 大类 12 个（cs.AI/cs.LG/cs.NI/cs.DC/cs.OS/cs.AR/cs.PF/cs.SE/cs.DB/cs.CR/cs.MA/cs.IT）+ eess 大类 3 个（eess.SP/eess.SY/eess.IT）+ math 大类 2 个（math.OC/math.PR）+ stat 大类 1 个（stat.ML）。分类清单应可配置（改配置文件即可调整）。
- **FR-1.2** `[Ubiquitous]` 采集后系统应对每篇论文执行**AI 相关性过滤**：判断论文是否含 AI/ML 方法成分，**仅保留有 AI 成分的论文**入库；非 AI 论文（纯通信理论、纯数学证明等）剔除。过滤的具体实现方式（规则/GLM/组合）在 plan 定。
- **FR-1.3** `[Ubiquitous]` 系统应按后台配置的关键词规则，将入库论文与**业务方向**（ADN、openFuyao、LLM_Agent）和**学术赛道**（网络自治、LLM Agent、分布式训练等，含默认赛道与细分赛道两层）打标关联。关键词规则写在配置文件中，管理员可改文件维护（可配置 UI → M4）。
- **FR-1.4** `[WHEN]` 管理员在后台点击"立即更新"时，系统应立即触发一次 arXiv 抓取，并实时返回进度（已抓取 / 总数）。
- **FR-1.5** `[Ubiquitous]` 每篇入库论文应记录：arxiv_id（唯一）、标题、作者列表、发布时间、摘要、分类、原始 RSS 条目、业务方向/学术赛道标签。
- **FR-1.6** `[IF]` 同一篇论文（arxiv_id 相同）被重复抓取，系统应跳过，不得重复入库。
- **FR-1.7** `[IF]` arXiv RSS 请求失败（超时、HTTP 错误），系统应记录到失败表（failed_jobs），不中断整个抓取批次。

### FR-2 实体识别（GLM 抽取）

- **FR-2.1** `[Ubiquitous]` 对每篇新入库论文，系统应调用 GLM-5.2 抽取：每位作者（姓名、作者顺序）、署名机构、研究方向标签。
- **FR-2.2** `[Ubiquitous]` GLM 输入策略：优先传论文全文（arXiv LaTeX/正文）；拿不到全文时传标题 + 摘要 + 作者列表。
- **FR-2.3** `[Ubiquitous]` GLM 应输出严格的结构化 JSON（schema 见 plan.md），代码解析后入库。**部分解析容错**：能解析的作者/字段正常入库；个别作者字段缺失走 FR-2.4 fallback；仅当整篇 JSON 无法解析时才视为失败走 FR-2.5 重试。
- **FR-2.4** `[Ubiquitous]` 作者机构信息通过 **GLM + OpenAlex 双源补充**（不预设主辅）：GLM 从论文全文/脚注抽取 + OpenAlex API 查询 author-institution，两源均拿不到时机构确信度记 0.4 兜底。
- **FR-2.5** `[IF]` GLM 调用失败（超时、限流、JSON 解析失败），系统应记录到 failed_jobs，按指数退避重试最多 3 次（1min/5min/25min）；3 次仍失败进入死信队列，后台可见、可手动重跑。

### FR-3 实体入库与消歧

- **FR-3.1** `[Ubiquitous]` 系统应维护 Person 实体（**姓名、机构、研究方向、openalex_id**）和 Organization 实体（名称、层级、官网、地点）。职位、联系方式、主页字段 M1 不做（→ M2/M3，待更可靠数据源上线）。
- **FR-3.2** `[WHEN]` 新作者出现时，系统应执行消歧：先用 openalex_id 强匹配（来自 FR-2.4）；命中则归并到已有 Person，未命中再用 5 因素加权（姓名 30% / 机构 25% / 研究方向 20% / 时间 15% / 合作网络 10%）打分。
- **FR-3.3** `[IF]` 消歧得分 ≥ 0.8，系统应自动归并；`[IF]` 得分在 0.5–0.8，应进入待审核队列；`[IF]` 得分 < 0.5，应创建新 Person。
- **FR-3.4** `[Ubiquitous]` 系统应提供**消歧审核最简入口**（M1 即做，不等 M4）：后台展示 0.5–0.8 待审核记录列表（含疑似同人的字段对比），管理员点击"合并"完成归并。完整审核 UI（批量操作、审核历史等）→ M4。

### FR-4 论文合作关系建立

- **FR-4.1** `[Ubiquitous]` 对每篇论文中任意两位作者 A、B，系统应建立一条 `paper_cooperation` 关系（人↔人）。
- **FR-4.2** `[Ubiquitous]` 每条关系应关联证据：那篇论文本身（Paper 实体）。
- **FR-4.3** `[Ubiquitous]` 每条关系应计算两个独立维度：
  - **身份置信度** = `0.4 × 姓名确信度 + 0.6 × 机构确信度`（衡量消歧可靠性，存疑关系打折并对接审核队列）；
  - **关系强度** = `身份置信度 × ( 单次基础分 + 按合作次数的阶梯加成 )`。spec 只定设计原则：① 单次合作不被压低（基础分 ≥ 0.8）；② 合作 N 次后快速触顶 1.0（N = 足以证明强关系的次数）；③ 阶梯跃升而非线性爬升；④ 超过 N 次不再加成。基础分、档位、N 的具体数值留 plan 调参。
- **FR-4.4** `[IF]` A、B 之间已存在 `paper_cooperation` 关系（来自其他论文），系统应合并：把新论文追加为证据、按 FR-4.3 阶梯加成重算关系强度、更新时间范围；不得新建重复关系。
- **FR-4.5** `[Ubiquitous]` 关系应记录：类型、**身份置信度、关系强度**（两个字段）、时间范围、最新证据时间、证据描述（如"基于 3 篇合作论文，最近合作于 2024 年"）。

### FR-5 图谱可视化与搜索

- **FR-5.1** `[Ubiquitous]` 系统应提供图谱主页，展示 Person 节点和 `paper_cooperation` 关系（实线）。
- **FR-5.2** `[WHEN]` 用户从预设筛选器中选择业务方向（ADN/openFuyao/LLM_Agent）或学术赛道时，系统应高亮该方向学者节点及其合作关系。M1 不提供研究方向自由文本搜索。
- **FR-5.3** `[WHEN]` 用户点击学者节点时，系统应展示该学者的详情（机构、研究方向、论文列表）。
- **FR-5.4** `[WHEN]` 用户点击一条合作关系时，系统应展示证据链（支撑论文列表，含标题/年份/会议）。
- **FR-5.5** `[Ubiquitous]` 系统应支持筛选：**姓名/机构用输入框**（自由输入，查询数据库匹配，数据随采集自动积累）；**研究方向/业务方向用预设筛选器**（选项来自后台配置文件，只能选不能自由输入）。结果可切换图谱/列表两种展示模式。
- **FR-5.6** `[Ubiquitous]` 系统应支持按关系强度过滤（隐藏低于阈值的关系）。

## 4. 非功能需求

- **NFR-1 性能**：图谱主页应支持展示至少 1000 个节点而不卡顿（节点聚合 + 分层）。
- **NFR-2 成本**：单篇论文 GLM 抽取目标控制在约 1500–3000 tokens；每日 token 用量受成本熔断约束（具体阈值在 plan.md 定）。
- **NFR-3 可观测**：后台应能看到 failed_jobs 列表、当日 GLM token 用量、数据更新状态。
- **NFR-4 兼容**：前端支持 Chrome/Edge/Firefox 最新版。

## 6. 验收标准（Acceptance Criteria）

> 满足以下全部条件，M1 视为完成。

- **AC-1**：配置好 arXiv 分类后，系统能自动拉取至少 50 篇论文并入库，每篇含完整的作者/机构/研究方向字段。
- **AC-2**：从预设筛选器选择某个学术赛道（如 network automation）或业务方向（如 ADN）后，能看到该方向学者间的论文合作网络（节点数 > 20，关系数 > 10）。
- **AC-3**：点击任意一条合作关系，能看到至少 1 篇支撑论文（标题、年份）。
- **AC-4**：按姓名（输入框）能搜到至少一位学者，并在图谱中定位到他。
- **AC-5**：同一对作者合作多篇论文时，关系不重复，证据合并正确，证据描述含"基于 N 篇"。
- **AC-6**：手动模拟 GLM 调用失败，failed_jobs 表有记录，重试机制按 1min/5min/25min 触发。
- **AC-7**：后台能看到当日 GLM token 用量和 failed_jobs 列表。
- **AC-8**：入库论文均通过 AI 相关性过滤（抽查非 AI 分类的论文，如 math.OC 中纯数学证明论文未入库）。
- **AC-9**：消歧审核队列可见待审核记录（0.5–0.8 区间），且管理员能通过最简审核入口成功合并两条记录为同一 Person。

## 7. 已确认决策（Resolved Decisions）

> review 过程中确认的关键决策，已固化。标注 *(默认)* 的为 review 时未明确反对、按推荐方案暂定，可在 plan 阶段前推翻。

- **RD-1（arXiv 采集分类）**：M1 跨大类采集 **18 个分类**：cs 大类 12 个（cs.AI/cs.LG/cs.NI/cs.DC/cs.OS/cs.AR/cs.PF/cs.SE/cs.DB/cs.CR/**cs.MA**/**cs.IT**）+ eess 大类 3 个（eess.SP/eess.SY/eess.IT）+ math 大类 2 个（math.OC/math.PR）+ stat 大类 1 个（stat.ML）。覆盖通用 AI + ADN（网络智能化）+ openFuyao（算力集群）+ **LLM/智能体**四个方向的技术栈（cs.MA/cs.IT 对齐 paper-insight 默认分类，2026-08-24 修订）。**严格 AI 相关性过滤**：仅保留含 AI 成分的论文入库，非 AI 论文（纯通信理论/纯数学证明）剔除。ADN/openFuyao/LLM_Agent 通过配置的关键词规则打标，不依赖 arXiv 分类。
- **RD-2（机构信息来源）**：**接入 OpenAlex**（免费、无需 key，建议带 `mailto` 参数提高 rate limit）。机构信息通过 **GLM + OpenAlex 双源补充**（不预设主辅），两源均拿不到时机构确信度 0.4 兜底。
- **RD-3（可视化组件）** *(默认)* ：M1 选用 **React Flow**。理由：React 原生集成、声明式、节点可自定义组件，适合 M1 的节点规模（几百到上千）和交互需求。若后续里程碑节点规模上万，再评估迁移到 Cytoscape.js。
- **RD-4（冷启动策略）** *(默认)* ：M1 **只做增量采集**（从上线日起每天拉新），不做大批量历史回灌。验收标准 AC-1 调整为"上线后累积 3-7 天，或手动触发一次小批量回灌（如近 1 个月），能凑足 50 篇"。大批量历史回灌（近 1-2 年）留给 M4。
- **RD-5（JSON Schema 定义时机）** *(默认)* ：spec 不写精确 JSON Schema，只列出"要抽取的字段"（见 FR-2.1）；精确 schema（字段名、类型、嵌套结构）留到 plan.md 定义。符合 SDD "spec 讲 what、plan 讲 how" 原则。
- **RD-6（业务方向体系）**：业务方向分两层——**产业方向**（ADN、openFuyao、LLM_Agent，参考 paper-insight 默认主题）和**学术赛道**（默认赛道：网络自治/网络数字孪生/意图网络/LLM Agent/多智能体/闭环自治；细分赛道：根因分析/流量预测/无线5G6G/分布式训练/算力调度/推理服务）。两者均写在后台配置文件（M1 硬编码，配置 UI → M4），用于采集后打标和前端筛选器。
- **RD-7（前端筛选模型）**：姓名/机构用**输入框**（自由输入查库匹配，数据随采集自动积累）；研究方向/业务方向用**预设筛选器**（只能选不能自由输入）。M1 不提供研究方向自由文本搜索。
- **RD-8（Person 字段裁剪）**：M1 Person 只留姓名/机构/研究方向/openalex_id；职位/联系方式/主页砍掉（→ M2/M3，待高校官网爬取等更可靠数据源）。
- **RD-9（消歧审核）**：M1 即做**最简审核入口**（待审核列表 + 字段对比 + 合并按钮），完整审核 UI → M4。
- **RD-10（置信度双层模型）**：拆分**身份置信度**（0.4×姓名 + 0.6×机构，衡量消歧可靠性）和**关系强度**（身份置信度 × (基础分 + 合作次数阶梯加成)）。设计原则：单次合作不被压低、合作 N 次快速触顶、阶梯跃升非线性、超 N 次不加成；数值留 plan。
- **RD-11（GLM 输出容错）**：部分解析容错——能解析的作者/字段入库，缺失字段走 fallback，仅整篇 JSON 无法解析才重试。
- **RD-12（性能口径）**：NFR-1 的"1000 节点"指单次图谱视图渲染上限，M1 保持此值；数据量增长后的聚合/分页优化 → 后续里程碑。
- **RD-13（中国学者范围，2026-08-31 用户补充）**：M1 只治理**含有中国学者**的论文（含其在国外机构任职），论文上的外国合作者及其机构一并保留；纯外国论文不建关系。落地方式：`papers.has_cn_scholar` 标记 + 启发式判定（中国机构关键词 / CJK 字符 / 中文姓氏拼音，任一命中即算，宁多勿漏——与 FR-1.2 过滤口径相反方向上从严）；GLM 细筛判定在周预算恢复后叠加（当周 6.01M/600 万已触顶，启发式先行兜底）。图谱 / 搜索 / 复核队列 / 筛选选项全部按此范围过滤。
