# 02-数据模型设计

## 核心设计理念

### 知识图谱视角

> **这是一张知识图谱，而不仅仅是关系数据库**

**关键特性**：
- 关系本身是实体，有独立的属性和证据
- 每个关系都必须有明确的证据链，确保可信度
- 关系的"为什么"是核心，支持追溯和验证

---

| 职位/职称 | 教授/副教授/讲师 | 教师主页 |

| 个人主页 | 教师/学者主页 URL | 教师/学者主页 |

**研究方向表示**：
- 使用多标签字段，如：["深度学习", "计算机视觉", "NLP"]
- 支持多个研究方向的同时表达

### Organization（机构）

## 关系模型设计

### 关系分类

**表内关系（传统外键关系）**：
- Person ↔ Paper（作者-发表-论文）
- Person ↔ Organization（作者-任职-机构）
- Paper ↔ Organization（论文-署名-机构）

**表外关系（知识图谱核心）**：

#### 直接关系（已验证）
- Person ↔ Person（直接关系）⭐
  - 第一阶段包含3种直接关系：论文合作、项目合作、学术传承
  - 存储表：relationships
  - 特征：有明确证据，置信度较高（0.3-1.0）

> **注意**：`relationships` 表**只存人↔人关系**。"顾问关系"（人↔机构）由于第一阶段无企业数据源，留到第二阶段，届时需扩展表结构支持人↔机构。

#### 同机构关系（辅助信号，非独立关系类型）

> "同机构"是一种**弱关系**，强度随粒度递减：**同组（实验室） > 同系 > 同院 > 同校**。

不作为独立关系存储，而是作为：
1. **学术传承关系的辅助推断信号**（同组 + 时间重叠 → 强化学术传承置信度）
2. **潜在关系 spatiotemporal（时空重叠）的输入信号**

#### 潜在关系（待发现）⭐新增
- Person ↔ Person（潜在关系）⭐⭐
  - 基于网络结构、内容相似性、时空重叠等多维度信号推导
  - 存储表：potential_relationships
  - 特征：基于推导，置信度相对较低（0.1-0.7），用于推荐和发现

**潜在关系第一阶段的3种发现方法**（均为人↔人）：

| 发现方法 | 说明 | 示例 |
|---------|------|-----|
| **common_network** | 基于共同网络的关系推断 | A和B都与C有合作 → A与B可能有合作关系 |
| **research_similarity** | 基于研究方向的相似性 | A和B的研究方向高度重合 → 可能形成协同效应 |
| **spatiotemporal** | 基于时空重叠的关联（含同机构信号） | A和B在同一时间段在同一机构 → 可能存在传承关系 |

> **role_match（角色匹配）移到第二阶段**：该方法是"教授在某企业任职 → 潜在校企合作"，属于人↔企业关系。第一阶段不接入企业数据源，暂不实现，等第二阶段建起 Enterprise 实体后再做。

### 关系的"证据链"设计

> **知识图谱的核心是回答"为什么"**

- 为什么 A 和 B 是合作关系？ → 因为他们共同发表了论文 X、Y、Z
- 为什么 A 和 C 是潜在合作关系？ → 因为他们都与 B 有合作关系，且研究方向相似

### 关系属性设计

**每个关系必须包含**：

| 属性 | 说明 | 示例 |
|-----|------|-----|
| **关系类型** | 论文合作/项目合作/学术传承 | "论文合作" |
| **证据列表** | 支撑该关系的证据对象 | [Paper1, Paper2, ...] 或 [Organization1] |
| **证据描述** | 人类可读的证据说明 | "基于论文：《Attention Is All You Need》等 3 篇" |
| **时间信息** | 关系的时间范围 | "2018-2024" 或 "最近合作：2024年" |
| **置信度** | AI 抽取的可靠性 | 0.95 |

### 证据链设计原则

> **每个关系都必须有明确的证据链，确保可信度**

**证据链示例**：

```
关系：张教授 —— 李教授
类型：论文合作
证据：
  - 论文：《Attention Is All You Need》（2018，NeurIPS）
  - 论文：《BERT: Pre-training of Deep Bidirectional Transformers》（2019，NAACL）
  - 论文：《GPT-3: Language Models are Few-Shot Learners》（2020，NeurIPS）
证据描述：基于 3 篇合作论文，最近合作于 2020 年
置信度：1.0（基于明确的论文数据）
```

**学术传承关系示例**：

```
关系：王教授 —— 赵教授
类型：学术传承（同组 + 时间重叠）
证据：
  - 机构：清华大学计算机系知识工程实验室（两人同期署名）
  - 时间：2018-2020 期间同在该实验室
证据描述：两人在 2018-2020 年间同属清华大学知识工程实验室（同组粒度）
置信度：0.9（同组 + 时间重叠，强信号）
```

> 注：上例中"同组"作为学术传承关系的**辅助推断信号**，并非独立关系类型。同机构粒度越细（同组 > 同系 > 同院 > 同校），对传承关系的置信度贡献越大。

### 设计原则

1. **所有关系必须有证据**：无证据的关系不存储
2. **证据必须是可追溯的**：证据对象本身存在于数据库中
3. **关系类型明确区分**：不同类型的关系有不同的语义
4. **置信度标注**：AI 抽取的关系必须标注可信度

## 数据库 Schema 设计

### 核心表结构

#### 1. persons（人员表）

```sql
CREATE TABLE persons (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    organization_id INTEGER REFERENCES organizations(id),
    research_tags TEXT[], -- 多标签研究方向
    position VARCHAR(50), -- 职位/职称
    contact_info TEXT, -- 联系方式
    bio TEXT, -- 个人简介
    homepage_url VARCHAR(500), -- 个人主页
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

#### 2. organizations（机构表）

```sql
CREATE TABLE organizations (
    id SERIAL PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    level VARCHAR(20), -- 'university'/'department'/'lab'
    website_url VARCHAR(500),
    location VARCHAR(100),
    created_at TIMESTAMP DEFAULT NOW()
);
```

#### 3. papers（论文表）

```sql
CREATE TABLE papers (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    publish_year INTEGER,
    source VARCHAR(200), -- 会议/期刊名称
    abstract TEXT,
    keywords TEXT[],
    doi VARCHAR(100),
    created_at TIMESTAMP DEFAULT NOW()
);
```

#### 4. relationships（直接关系表）

```sql
CREATE TABLE relationships (
    id SERIAL PRIMARY KEY,
    person1_id INTEGER REFERENCES persons(id),
    person2_id INTEGER REFERENCES persons(id),
    relationship_type VARCHAR(50) NOT NULL, -- 'paper_cooperation'/'project_cooperation'/'academic_mentorship'
    confidence FLOAT DEFAULT 1.0,
    time_range VARCHAR(50), -- 如 "2018-2024"
    latest_evidence_time TIMESTAMP,
    evidence_description TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    UNIQUE(person1_id, person2_id, relationship_type)
);
```

#### 4.1. potential_relationships（潜在关系表）

```sql
CREATE TABLE potential_relationships (
    id SERIAL PRIMARY KEY,
    person1_id INTEGER REFERENCES persons(id),
    person2_id INTEGER REFERENCES persons(id),
    discovery_method VARCHAR(50) NOT NULL, -- 'common_network'/'research_similarity'/'spatiotemporal'
    confidence FLOAT DEFAULT 0.5,
    discovery_reason TEXT, -- 发现原因描述
    supporting_signals JSONB, -- 支持信号（如共同合作者数量、研究相似度分数等）
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    UNIQUE(person1_id, person2_id, discovery_method)
);

-- 支持信号 JSONB 结构示例
-- {
--   "common_collaborators": ["person_id_3", "person_id_5"],
--   "common_collaborator_count": 2,
--   "research_similarity_score": 0.85,
--   "common_organizations": ["org_id_1"],
--   "time_overlap": "2018-2020"
-- }
```

**潜在关系 vs 直接关系**：

| 特性 | 直接关系 | 潜在关系 |
|-----|---------|---------|
| **证据类型** | 有明确证据（论文、项目等） | 基于推导和推断 |
| **置信度范围** | 0.3-1.0 | 0.1-0.7 |
| **更新频率** | 有新证据时更新 | 定期重新计算 |
| **用途** | 展示已知关系 | 推荐潜在合作机会 |

#### 5. evidence（证据表）

```sql
CREATE TABLE evidence (
    id SERIAL PRIMARY KEY,
    relationship_id INTEGER REFERENCES relationships(id),
    evidence_type VARCHAR(50) NOT NULL, -- 'paper'/'organization'/'news'/'project'
    evidence_id INTEGER NOT NULL, -- paper_id 或 organization_id
    evidence_description TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);
```

#### 6. person_paper_affiliation（作者-论文-机构关联表）

```sql
CREATE TABLE person_paper_affiliation (
    id SERIAL PRIMARY KEY,
    person_id INTEGER REFERENCES persons(id),
    paper_id INTEGER REFERENCES papers(id),
    organization_id INTEGER REFERENCES organizations(id),
    author_order INTEGER, -- 作者顺序
    created_at TIMESTAMP DEFAULT NOW(),
    UNIQUE(person_id, paper_id, organization_id)
);
```

### 设计说明

1. **证据单独存储**：证据表记录每个关系的具体证据，支持追溯和查询
2. **关系唯一性**：通过 UNIQUE 约束确保相同两人、相同类型的关系只存一条
3. **时间信息**：关系表记录时间范围和最新证据时间
4. **灵活的标签存储**：使用 TEXT[] 存储多标签（研究方向、关键词）

## 实体消歧机制

### 核心挑战

**同一人名可能指向不同的人**：
- "张伟"在中国可能有成千上万个
- 同一个人在不同论文中可能有不同的名字表述
- 需要准确识别并合并同一人的多个实体

### 消歧流程

```
新人名出现 → 多因素匹配 → 置信度评估 → 决策
  ↓              ↓             ↓           ↓
姓名相似度    机构匹配      计算合并概率  合并/新建
拼音/英文名   时间重叠      设置阈值      记录决策
研究方向     论文网络
```

### 消歧因素与权重

| 消歧因素 | 说明 | 权重 |
|---------|------|------|
| **姓名相似度** | 拼音、英文变体（如"张伟" vs "Wei Zhang"） | 30% |
| **机构匹配度** | 是否在同一机构或有机构重叠 | 25% |
| **研究方向相似度** | 研究方向的重合程度 | 20% |
| **时间重叠度** | 活跃时间段的重叠 | 15% |
| **论文网络关联** | 是否有共同作者 | 10% |

### 消歧算法

**步骤1：姓名候选筛选**
```python
# 对于新人名new_person
candidates = find_name_similar_persons(new_person, similarity_threshold=0.7)
```

**步骤2：多因素匹配评分**
```python
for candidate in candidates:
    score = (
        0.3 * name_similarity(new_person, candidate) +
        0.25 * organization_overlap(new_person, candidate) +
        0.2 * research_similarity(new_person, candidate) +
        0.15 * time_overlap(new_person, candidate) +
        0.1 * paper_network_connection(new_person, candidate)
    )
```

**步骤3：决策**
```python
if score > 0.8:
    # 高置信度：自动合并
    merge_persons(new_person, candidate)
elif score > 0.5:
    # 中置信度：进入待审核队列
    add_to_review_queue(new_person, candidate, score)
else:
    # 低置信度：创建新实体
    create_new_person(new_person)
```

### 消歧错误修正

**人工审核机制**：
- 在管理后台提供消歧审核界面
- 显示待审核的候选合并
- 人工确认或拒绝合并建议

**合并操作**：
- 将一个实体的所有关系和证据转移到另一个实体
- 删除被合并的实体
- 记录合并日志，支持撤销操作

## 关系去重机制

### 核心挑战

**同一关系可能从多个数据源被发现**：
- 同一合作关系在多篇论文中出现
- 同一项目合作关系在多个资讯源中报道
- 需要合并证据，避免重复存储

### 去重策略

**数据库层面的约束**：
```sql
-- relationships 表的唯一约束
UNIQUE(person1_id, person2_id, relationship_type)
```

**合并逻辑**：
```
发现新关系 → 检查是否已存在 → 决策
  ↓             ↓                ↓
从新证据提取  查询现有关系    更新/插入
识别关系信息  比较关系类型    合并证据
              合并证据链       更新置信度
```

### 证据合并算法

**步骤1：检查现有关系**
```sql
SELECT * FROM relationships
WHERE person1_id = A AND person2_id = B AND relationship_type = 'paper_cooperation'
```

**步骤2：如果存在，合并证据**
```python
if existing_relationship:
    # 添加新证据
    add_evidence(existing_relationship.id, new_evidence)
    
    # 更新证据描述
    existing_relationship.evidence_description = (
        f"基于 {count_evidence(existing_relationship)} 篇合作论文，"
        f"最近合作于 {get_latest_evidence_time(existing_relationship)} 年"
    )
    
    # 更新置信度（取最高值或重新计算）
    existing_relationship.confidence = max(
        existing_relationship.confidence,
        new_evidence.confidence
    )
    
    # 更新时间信息
    update_time_range(existing_relationship)
else:
    # 创建新关系
    create_relationship(person1_id, person2_id, relationship_type, new_evidence)
```

### 证据链更新

**时间范围更新**：
```python
def update_time_range(relationship):
    evidences = get_all_evidences(relationship.id)
    years = [evidence.year for evidence in evidences if evidence.year]
    if years:
        relationship.time_range = f"{min(years)}-{max(years)}"
        relationship.latest_evidence_time = max(evidence.created_at for evidence in evidences)
```

**置信度更新策略**：
- **取最高值**：confidence = max(old_confidence, new_confidence)
- **加权平均**：confidence = weighted_average([old_confidence, new_confidence], weights=[old_evidence_count, 1])
- **重新计算**：根据该关系的所有证据重新计算置信度

### 去重日志

记录所有关系合并操作，支持追溯：
```sql
CREATE TABLE relationship_merge_log (
    id SERIAL PRIMARY KEY,
    relationship_id INTEGER REFERENCES relationships(id),
    evidence_id INTEGER REFERENCES evidence(id),
    action VARCHAR(20), -- 'merge'/'update'/'create'
    description TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);
```

## 证据链处理逻辑

### 正确的流程

> **先有证据 → 识别关系 → 提取保存证据**

### 流程说明

```
原始数据（论文、资讯）
  ↓
【证据提取】保存原始证据对象
  ↓
【实体识别】GLM 识别人员、机构
  ↓
【关系识别】基于证据识别关系类型
  ↓
【关系存储】建立关系 + 关联证据
```

### 数据库逻辑

1. **先存证据**：论文、资讯作为独立实体存入数据库
2. **再识关系**：基于证据实体识别人员之间的关系
3. **关联证据**：关系表关联证据表，支持追溯

### 示例流程

```
1. 获取论文《Attention Is All You Need》
   → 存入 papers 表（id=1）

2. GLM 识别实体
   → 识别出作者：Ashish Vaswani, ...
   → 识别出机构：Google Brain

3. 建立关系
   → 发现 Ashish Vaswani 与其他作者有合作关系
   → 存入 relationships 表

4. 关联证据
   → 存入 evidence 表，关联 paper_id=1
   → 支持追溯："为什么他们是合作关系？因为共同发表了这篇论文"
```

## 潜在关系挖掘逻辑

### 核心流程

> **基于已有关系网络 → 发现潜在关联 → 计算置信度 → 存储推荐**

### 流程说明

```
已有关系网络（从 relationships 表构建）
  ↓
【网络分析】计算节点之间的潜在关联
  ↓
【多特征融合】综合网络位置、内容相似度等信号
  ↓
【置信度评估】为潜在关系评分
  ↓
【潜在关系存储】存入 potential_relationships 表
```

### 3种潜在关系发现方法详解（第一阶段，均为人↔人）

> **role_match（角色匹配）已移到第二阶段**：该方法是"教授在某企业任职 → 潜在校企合作"，属于人↔企业关系。第一阶段不接入企业数据源，暂不实现。

#### 方法1：common_network（共同网络）

**原理**：如果两人有共同合作者，他们之间可能存在潜在合作关系

**算法**：
```
对于任意人员A和B：
1. 查找A的合作者列表：collaborators_A
2. 查找B的合作者列表：collaborators_B
3. 计算共同合作者：common = collaborators_A ∩ collaborators_B
4. 如果 common 不为空：
   - 计算置信度 = f(共同合作者数量, 网络距离)
   - 存储潜在关系
```

**示例**：
- A与C合作过，B与C也合作过
- 推断：A与B可能有潜在合作关系

#### 方法2：research_similarity（研究相似性）

**原理**：研究方向相似的人可能形成协同效应

**算法**：
```
对于任意人员A和B：
1. 获取A的研究方向向量：embedding_A = embed(["深度学习", "计算机视觉"])
2. 获取B的研究方向向量：embedding_B = embed(["深度学习", "NLP"])
3. 计算研究方向相似度（余弦相似度）：
   - 相似度 = cosine(embedding_A, embedding_B)
   - 注：使用 Embedding 而非 Jaccard，以解决"NLP/自然语言处理/natural language processing"等同义标签问题
4. 如果相似度 > 阈值（如0.3）：
   - 计算置信度 = g(相似度, 研究热度)
   - 存储潜在关系
```

**示例**：
- A研究"深度学习"和"计算机视觉"
- B研究"深度学习"和"NLP"
- 推断：A与B有共同研究方向，可能形成协同效应

#### 方法3：spatiotemporal（时空重叠，含同机构信号）

**原理**：同一时间段在同一机构的人可能存在学术传承关系

**算法**：
```
对于任意人员A和B：
1. 获取A的机构历史：orgs_A = [(清华大学, 2015-2018), (斯坦福, 2018-2020)]
2. 获取B的机构历史：orgs_B = [(清华大学, 2016-2019)]
3. 检查时空重叠：
   - 是否有共同机构？是（清华大学）
   - 时间是否重叠？是（2016-2018）
   - 同机构粒度：同组 > 同系 > 同院 > 同校（粒度越细权重越高）
4. 如果有重叠：
   - 计算置信度 = h(重叠时长, 机构粒度)
   - 存储潜在关系
```

**示例**：
- A：2015-2018年在清华大学
- B：2016-2019年在清华大学
- 推断：A与B可能存在学术传承关系

### 潜在关系的置信度评估

#### common_network 置信度公式

```
置信度 = 0.5 × 共同合作者归一化 + 0.3 × 网络距离归一化 + 0.2 × 机构相似度
```

| 因子 | 计算方式 | 权重 |
|-----|---------|------|
| 共同合作者归一化 | min(共同合作者数/5, 1.0) | 50% |
| 网络距离归一化 | 1.0/(网络距离+1) | 30% |
| 机构相似度 | 是否同机构（1.0/0.5） | 20% |

#### research_similarity 置信度公式

```
置信度 = 0.7 × 研究方向相似度 + 0.3 × 研究热度因子
```

| 因子 | 计算方式 | 权重 |
|-----|---------|------|
| 研究方向相似度 | Jaccard相似度 | 70% |
| 研究热度因子 | 该方向的论文数量/活跃度 | 30% |

#### spatiotemporal 置信度公式

```
置信度 = 0.4 × 重叠时长 + 0.4 × 同机构粒度 + 0.2 × 角色相似度
```

| 因子 | 计算方式 | 权重 |
|-----|---------|------|
| 重叠时长 | min(重叠年数/5, 1.0) | 40% |
| 同机构粒度 | 同组(1.0)/同系(0.7)/同院(0.5)/同校(0.3) | 40% |
| 角色相似度 | 同为教授/学生等(1.0)否则(0.5) | 20% |

> 注：role_match（角色匹配）的置信度公式移到第二阶段补充。

### 潜在关系的更新策略

**定期重新计算**：
- 频率：每周一次
- 原因：新的直接关系可能改变潜在关系的置信度

**触发式更新**：
- 当有新的直接关系建立时
- 重新计算相关人员的潜在关系
