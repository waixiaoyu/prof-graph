## LLM API 调用设计

### GLM 接口配置

**使用智谱 GLM 的 Anthropic 协议接口**

```javascript
const llmConfig = {
  mode: "glm-coding-anthropic",
  protocol: "anthropic",
  model: "glm-5.2",
  endpoint: "https://open.bigmodel.cn/api/anthropic/v1/messages",

  // 环境变量映射
  apiKey: () => process.env.GLM_CODING_API_KEY || process.env.LLM_API_KEY,
  modelEnv: () => process.env.GLM_CODING_MODEL || process.env.LLM_MODEL,
  endpointEnv: () => process.env.GLM_CODING_ANTHROPIC_API_URL || process.env.LLM_API_URL,
};
```

### GLM 调用函数

```javascript
async function callGLM(prompt, options = {}) {
  const config = llmConfig;
  const controller = new AbortController();

  // 超时控制（默认 10 分钟）
  const timeout = setTimeout(() => controller.abort(), options.timeout || 600000);

  try {
    const payload = {
      model: config.model,
      temperature: options.temperature || 0.1,
      max_tokens: options.max_tokens || 4000,
      messages: [
        {
          role: "system",
          content: options.systemPrompt || "你是学术论文实体识别助手。"
        },
        {
          role: "user",
          content: String(prompt)
        }
      ]
    };

    // Anthropic 协议：将 system 消息单独提取
    const [systemMessage, userMessage] = payload.messages;
    payload.system = systemMessage.content;
    payload.messages = [userMessage];

    const response = await fetch(config.endpoint, {
      method: "POST",
      signal: controller.signal,
      headers: {
        "authorization": `Bearer ${config.apiKey()}`,
        "x-api-key": config.apiKey(),
        "anthropic-version": "2023-06-01",
        "content-type": "application/json"
      },
      body: JSON.stringify(payload)
    });

    if (!response.ok) {
      throw new Error(`GLM API error: ${response.status}`);
    }

    const data = await response.json();

    // Anthropic 协议响应格式
    return data.content?.[0]?.text || "";

  } finally {
    clearTimeout(timeout);
  }
}
```

### 关键技术要点

1. **协议要求**：GLM 使用 Anthropic 协议，需要特殊的请求头（x-api-key, anthropic-version）
2. **请求格式**：system 消息需要单独提取，不是放在 messages 数组中
3. **端点格式**：必须以 `/v1/messages` 结尾
4. **超时控制**：使用 AbortController 实现超时机制
5. **成本控制**：通过 max_tokens 控制 API 调用成本

## LLM 抽取工程细节 ⭐

> 本章节是第一阶段最大的技术风险点，明确 GLM 抽取的输入、输出、机构补全、失败处理、调度方案。

### 输入策略（能传全文就传全文）

| 数据源 | 传给 GLM 的内容 | 备注 |
|--------|--------------|------|
| arXiv 论文 | **优先传全文**（LaTeX/正文）；拿不到全文则传**标题 + 摘要 + 作者列表** | arXiv 多数有 LaTeX 源码，全文可得；2026-08-30 加固：全文输入头部统一拼 RSS 标题+作者列表（arXiv HTML 作者区块可能被转换丢弃），LaTeXML 转换失败残页视同全文不可用（specs/M1 §9 附录） |
| RSS 资讯 | **资讯标题 + 正文** | 资讯正文一般不长，可直接传 |
| 高校官网 | **教师主页/实验室页面的正文 HTML 转文本** | 爬虫已抓到页面，直接喂给 GLM |

**作者列表的特殊处理**：arXiv 的作者列表是结构化的（有作者顺序），但**作者单位（机构）经常缺失或需要语义抽取**。因此作者名虽可直接解析，但机构仍需 GLM 或外部 API 补全（见下）。

### 机构抽取：多级 fallback 策略 ⭐

机构是论文合作置信度的关键依赖（占 60% 权重），但 arXiv 论文机构信息普遍缺失，需要分级补全：

```
步骤1：GLM 理解论文
  - 从论文全文/脚注/致谢/affiliation 字段抽取每个作者的机构
  - 输出结构化机构列表（含标准化名称、层级、地点）
       ↓ 若 GLM 仍未抽到机构
步骤2：外部 API 补全
  - 调用 OpenAlex API（免费、覆盖率高、有 author-institution 映射）
  - 用作者名 + 论文标题查询，拿到 author_id → institution
  - 或 Semantic Scholar API 作为备选
       ↓ 若外部 API 也拿不到
步骤3：默认值兜底
  - 机构确信度记为 0.4（"机构不明确或缺失"）
  - 论文合作置信度按公式正常计算（会被拉低）
```

### 失败处理：失败表 + 重试 + 死信队列

每天处理 150+ 篇论文，必须考虑 GLM 调用失败的情况：

```
抽取任务执行
  ↓
  ├─ 成功 → 解析 JSON → 入库
  └─ 失败（超时/限流/格式错误）
       ↓
       记录到 failed_jobs 表（含原始输入、失败原因、失败时间）
       ↓
       重试机制（最多 3 次，间隔指数递增：1min / 5min / 25min）
       ↓
       ├─ 重试成功 → 入库
       └─ 3 次仍失败 → 进入死信队列（dead_letter_queue）
                        ↓
                        后台管理界面可见，支持手动重跑
```

**failed_jobs 表设计**：

```sql
CREATE TABLE failed_jobs (
    id SERIAL PRIMARY KEY,
    job_type VARCHAR(50) NOT NULL,          -- 'paper_extraction'/'rss_extraction'/'website_crawl'
    source_id VARCHAR(200),                 -- 论文 arxiv_id / 资讯 url / 网页 url
    input_payload JSONB,                    -- 原始输入（用于重跑）
    error_message TEXT,
    retry_count INTEGER DEFAULT 0,
    status VARCHAR(20) DEFAULT 'pending',   -- 'pending'/'retrying'/'dead'/'resolved'
    next_retry_at TIMESTAMP,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### 任务调度：APScheduler（应用内调度）

**选择 APScheduler**，理由：单机内部系统，把"定时闹钟"装在 FastAPI 进程里，网站和定时任务一体化，后台"立即更新"按钮能直接触发，任务状态网站里可见，无需额外组件（不用 Celery+Redis）。

**调度任务配置**：

```python
from apscheduler.schedulers.asyncio import AsyncIOScheduler
from apscheduler.triggers.cron import CronTrigger

scheduler = AsyncIOScheduler()

# 每天凌晨 2 点：拉取 arXiv + RSS 新数据
scheduler.add_job(daily_data_fetch, CronTrigger(hour=2, minute=0))

# 每天凌晨 3 点：对新数据执行 GLM 抽取
scheduler.add_job(daily_extraction, CronTrigger(hour=3, minute=0))

# 每周日凌晨 4 点：重新计算潜在关系
scheduler.add_job(weekly_potential_recompute, CronTrigger(day_of_week='sun', hour=4, minute=0))

# 每天凌晨 5 点：数据备份
scheduler.add_job(daily_backup, CronTrigger(hour=5, minute=0))

scheduler.start()
```

**手动触发**：后台"立即更新"按钮通过 API 直接调用对应的 job 函数，并返回任务执行进度。

## 自动化流程技术决策

### 决策 1：LLM 调用策略

**选择：全量 LLM 调用**

- 每篇论文都调用 GLM 进行实体识别和关系抽取
- 成本：每篇论文约 1000-2000 tokens
- 优势：准确度最高，实现简单
- 成本控制：通过 max_tokens 和批量处理优化

### 决策 2：实体消歧策略

**基于多因素的消歧方法**：

1. **姓名相似度**：使用字符串相似度算法（如 Levenshtein 距离、Jaccard 相似度）
2. **机构匹配**：比较机构的层级和名称相似度
3. **研究内容**：比较研究方向的重合度
4. **时间维度**：检查活跃时间段的重叠
5. **网络关联**：检查是否有共同合作者

**消歧流程**：
```
新人名出现 → 检查是否与现有人名相似 →
  机构相同？→ 很可能是同一人 → 合并
  机构不同？→ 检查论文网络 → 有共同作者？→ 可能同一人 → LLM 确认
    → 不同人 → 创建新实体
```

**技术实现**：

**姓名相似度计算**：
```python
from difflib import SequenceMatcher

def name_similarity(name1, name2):
    # 完全匹配
    if name1 == name2:
        return 1.0

    # 拼音匹配（中文转拼音后比较）
    pinyin1 = to_pinyin(name1)
    pinyin2 = to_pinyin(name2)
    if pinyin1 == pinyin2:
        return 0.9

    # 字符串相似度
    similarity = SequenceMatcher(None, name1, name2).ratio()
    return similarity
```

**多因素评分**：
```python
def calculate_merge_score(candidate1, candidate2):
    score = 0.0

    # 姓名相似度 (30%)
    score += 0.3 * name_similarity(candidate1.name, candidate2.name)

    # 机构匹配度 (25%)
    score += 0.25 * organization_match(candidate1, candidate2)

    # 研究方向相似度 (20%)
    score += 0.2 * research_similarity(candidate1.research_tags, candidate2.research_tags)

    # 时间重叠度 (15%)
    score += 0.15 * time_overlap(candidate1.active_period, candidate2.active_period)

    # 论文网络关联 (10%)
    score += 0.1 * has_common_collaborators(candidate1, candidate2)

    return score
```

**决策逻辑**：
```python
def deduplicate_person(new_person):
    candidates = find_similar_persons(new_person, threshold=0.7)

    for candidate in candidates:
        score = calculate_merge_score(new_person, candidate)

        if score >= 0.8:
            # 高置信度：自动合并
            merge_persons(new_person, candidate)
            return
        elif score >= 0.5:
            # 中置信度：进入审核队列
            add_to_review_queue(new_person, candidate, score)
            return

    # 无合适候选：创建新实体
    create_new_person(new_person)
```

**LLM 辅助确认**（用于中置信度情况）：

### 决策 2.5：关系去重策略 ⭐新增

def process_relationship(person1_id, person2_id, relationship_type, new_evidence):

    existing = query_relationship(person1_id, person2_id, relationship_type)

    if existing:

### 决策 2.6：潜在关系挖掘策略 ⭐新增

**选择：多特征融合的图算法方法**

潜在关系挖掘是系统最具挑战性的部分，采用以下策略：

1. **基于图算法的网络分析**
   - 使用 NetworkX 或 iGraph 构建关系网络图
   - 应用共同邻居算法发现潜在连接
   - 计算节点之间的最短路径和网络距离

2. **基于内容相似性的匹配**
   - 使用余弦相似度计算研究方向的重合度
   - 使用 TF-IDF 或 Embedding 方法提取研究主题
   - 相似度超过阈值的关系作为候选

3. **定期批量计算**
   - 每周重新计算一次潜在关系
   - 新的直接关系建立时触发局部更新
   - 使用缓存优化计算性能

**技术实现栈**：
- **图计算**：NetworkX（Python）或 iGraph
- **相似度计算**：scikit-learn 或 sentence-transformers
- **任务调度**：Celery 或 APScheduler
- **数据库查询**：SQL 图遍历查询（PostgreSQL 递归 CTE）

### 决策 3：数据更新频率

**每天更新一次**：

- **时间**：每天凌晨自动执行
- **范围**：抓取前一天的新论文（arXiv 每天 100-200 篇 cs.AI/cs.LG 论文）
- **流程**：获取 → 抽取 → 入库 → 更新关系

### 批量处理优化

为了提高效率，采用批量处理：

```javascript
// 每次处理 10 篇论文，减少 API 调用次数
async function processPapersInBatch(papers) {
  const batchSize = 10;
  for (let i = 0; i < papers.length; i += batchSize) {
    const batch = papers.slice(i, i + batchSize);
    await callGLMForBatch(batch);
  }
}
```

### 成本估算

假设每天 150 篇新论文，每篇 1500 tokens：

- **输入**：150 篇 × 1500 tokens = 225,000 tokens/day
- **输出**：150 篇 × 2000 tokens = 300,000 tokens/day
- **月成本**：约 525,000 tokens × 30 天 × GLM 价格

具体成本需要根据 GLM-5.2 的定价计算。

- ❌ 智能推荐系统（基于潜在关系的主动推荐功能，后续迭代）
- ❌ AI 问答（后续迭代）

**说明**：
- 第一阶段包含**潜在关系挖掘**（发现和计算），但**不包含智能推荐系统**（基于挖掘结果进行主动推荐）。潜在关系挖掘的结果将在图谱中以"潜在连接"的形式展示给用户。
- **关于"爬取"的措辞约定**：RSS = 第一阶段，网页爬虫 = 第二阶段。唯一例外是**高校官网爬取**（学术传承关系的唯一可靠数据源），特例纳入第一阶段。

## 开发时间周期：按里程碑交付

> 不绑死具体周数，按里程碑迭代交付。每个里程碑结束时有独立可验收的成果。

### 里程碑 M1：论文合作全链路 MVP

**目标**：跑通"arXiv RSS → GLM 抽取 → 论文合作关系入库 → 图谱展示"的最小闭环。

- 数据库 Schema 设计（persons / papers / organizations / relationships / evidence 等核心表）
- arXiv RSS 拉取 + APScheduler 定时任务
- GLM 实体识别（作者、机构、研究方向）+ 机构抽取 fallback（GLM 理解论文 → OpenAlex 等外部 API 补全）
- 论文合作关系抽取 + 证据链
- 基础前端图谱可视化 + 搜索

**验收**：能在图谱里看到某领域的论文合作网络。

### 里程碑 M2：学术传承 + 项目合作

**目标**：补全另外 2 种直接关系的数据源和抽取链路。

- 高校官网爬取（教师主页、实验室成员、毕业生名单、论文致谢）
- 学术传承关系抽取（含同机构粒度辅助信号）
- RSS 资讯（机器之心等）解析 + 项目合作关系抽取
- 实体消歧（OpenAlex author ID 兜底 + 5 因素加权）
- 关系去重与证据合并

**验收**：图谱里能看到 3 种直接关系的混合网络。

### 里程碑 M3：潜在关系挖掘

**目标**：基于已有直接关系网络，跑通潜在关系计算。

- common_network（共同网络）算法实现
- research_similarity（Embedding 研究相似度）算法实现
- spatiotemporal（时空重叠 + 同机构粒度）算法实现
- 潜在关系在图谱中以"潜在连接"形式展示
- 后台管理（消歧审核队列、手动编辑、立即更新）

**验收**：图谱里能看到潜在连接，且能追溯其推断依据。

### 里程碑 M4：稳定性与体验打磨

- GLM 失败处理（失败表 + 重试 + 死信队列）
- 成本熔断（每日 token 上限 + 告警）
- 数据监控页面（更新状态、新增实体、系统健康）
- 合规处理（robots.txt 遵守、敏感字段加密、删除接口）

具体每个里程碑的耗时根据实际开发情况调整。
