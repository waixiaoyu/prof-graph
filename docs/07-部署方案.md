# 07-部署方案

## 部署方式：本地部署

### 选择理由

- **数据安全**：所有数据在本地
- **部署简单**：不需要复杂的服务器配置
- **单机使用**：无需考虑多用户并发

---

## 系统架构

```
本地机器
├── PostgreSQL 数据库（本地安装或 Docker）
├── Python 后端服务（FastAPI）
├── React 前端（静态文件）
└── 定时任务脚本（数据更新）
```

---

## 数据更新机制

### 调度方式：APScheduler（应用内调度）

> 选择 **APScheduler**：把定时任务装进 FastAPI 进程里，与网站一体化。后台"立即更新"按钮可直接触发任务，任务状态网站内可见，无需额外组件（不用 Celery + Redis）。
>
> 详细的任务配置见 [03-技术架构设计.md - 任务调度](./03-技术架构设计.md#任务调度apscheduler应用内调度)。

### 两种触发方式

#### 1. 自动更新（APScheduler 定时任务）

- **时间**：
  - 每天凌晨 2 点：拉取 arXiv RSS + AI 媒体 RSS + 高校官网新内容
  - 每天凌晨 3 点：对新数据执行 GLM 抽取
  - 每周日凌晨 4 点：重新计算潜在关系
  - 每天凌晨 5 点：数据备份
- **流程**：获取 → 抽取 → 入库 → 更新关系

#### 2. 手动触发

- 在管理后台提供"立即更新"按钮（直接调用 APScheduler 的 job 函数）
- 实时显示更新进度
- 更新完成后刷新数据

## 运行环境要求

### 最低配置

| 资源 | 要求 | 说明 |
|-----|------|------|
| **CPU** | 4 核心以上 | 用于 GLM 调用和数据处理 |
| **内存** | 8GB 以上 | 用于数据库和缓存 |
| **存储** | 50GB 以上 | 用于数据库 + 论文缓存 |
| **网络** | 稳定的网络连接 | 用于调用 GLM API |

### 软件依赖

- **Python 3.10+**
- **Node.js 18+**（前端构建）
- **PostgreSQL 14+**
- **浏览器**：Chrome/Edge/Firefox 最新版

## 定时任务配置

> 定时任务由应用内的 **APScheduler** 管理（随 FastAPI 进程启动），不再依赖系统 cron 或 Windows 任务计划。详细配置见 [03-技术架构设计.md - 任务调度](./03-技术架构设计.md#任务调度apscheduler应用内调度)。

### 调度任务清单

| 任务 | 频率 | 说明 |
|------|------|------|
| 数据抓取 | 每天凌晨 2 点 | arXiv RSS + AI 媒体 RSS + 高校官网爬取 |
| GLM 抽取 | 每天凌晨 3 点 | 对新数据执行实体识别和关系抽取 |
| 潜在关系重算 | 每周日凌晨 4 点 | 重新计算 common_network / research_similarity / spatiotemporal |
| 数据备份 | 每天凌晨 5 点 | PostgreSQL 全量备份 |

## 合规与成本控制

### 合规处理

系统从公开渠道（arXiv、RSS、高校官网）采集个人信息建图谱，需注意合规：

| 合规项 | 处理方式 |
|--------|---------|
| **遵守 robots.txt** | 高校官网爬取前检查 robots.txt，禁止抓取的路径不爬 |
| **仅采集公开信息** | 不采集需要登录、付费、私密渠道才能获取的数据 |
| **遵守数据源 ToS** | 各数据源的服务条款，明确禁止抓取的源不接入 |
| **敏感字段加密** | 个人邮箱、电话等敏感字段在数据库中加密存储 |
| **删除接口** | 提供数据删除接口，支持按人员删除其所有关联数据 |

### GLM 成本熔断 ⭐

为避免 arXiv 某天大更新等原因导致 GLM 账单失控，设置成本熔断机制：

```python
# 每日 token 上限（可根据实际情况调整）
DAILY_TOKEN_BUDGET = 2_000_000  # 每日 200 万 tokens

# 监控逻辑
async def check_budget_before_call():
    today_usage = get_today_token_usage()
    if today_usage >= DAILY_TOKEN_BUDGET:
        # 触发熔断：暂停抽取任务，发告警
        pause_extraction_jobs()
        send_alert(f"GLM 日成本熔断：今日已用 {today_usage} tokens")
        return False
    return True
```

| 熔断项 | 阈值（建议） | 处理 |
|--------|-----------|------|
| 每日 token 上限 | 200 万 tokens | 超过则暂停当日抽取任务，次日自动恢复 |
| 单次任务失败率 | > 30% | 暂停任务并告警，避免连环失败浪费成本 |
| 月度成本上限 | 可配置 | 超过则停止所有非必要 GLM 调用 |

## 常见问题

### Q1: GLM API 调用失败

**检查**：
1. API Key 是否正确配置
2. 网络连接是否正常
3. API 端点是否正确

### Q2: 数据库连接失败

**检查**：
1. PostgreSQL 服务是否运行
2. 数据库配置是否正确
3. 端口是否被占用

### Q3: 前端无法连接后端

**检查**：
1. 后端服务是否运行
2. API URL 是否正确
3. 端口是否正确
