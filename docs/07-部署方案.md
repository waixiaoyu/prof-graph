# 07-部署方案

> **状态注记（2026-08-29 修订）**：本文档为设计参考资料，实现以 `specs/` 为准（constitution §7）。调度时间表、环境变量名、端口、预算数值已按当前实现修订；仍有冲突时以 specs 与 `backend/.env.example` 为准。

## 部署方式：本地部署

### 选择理由

- **数据安全**：所有数据在本地
- **部署简单**：不需要复杂的服务器配置
- **单机使用**：无需考虑多用户并发

---

## 系统架构

```
本地机器
├── PostgreSQL 数据库（本地安装或 Docker）
├── Python 后端服务（FastAPI）
├── React 前端（静态文件）
└── 定时任务脚本（数据更新）
```

---

## 数据更新机制

### 调度方式：APScheduler（应用内调度）

> 选择 **APScheduler**：把定时任务装进 FastAPI 进程里，与网站一体化。后台"立即更新"按钮可直接触发任务，任务状态网站内可见，无需额外组件（不用 Celery + Redis）。
>
> 详细的任务配置见 [03-技术架构设计.md - 任务调度](./03-技术架构设计.md#任务调度apscheduler应用内调度)。

### 两种触发方式

#### 1. 自动更新（APScheduler 定时任务）

- **时间**（时区 Asia/Shanghai，随 FastAPI 进程内的 APScheduler 注册）：
  - 每天凌晨 2 点 ±5min：全库备份（pg_dump 自定义格式，滚动保留 7 份，刻意早于采集链——管线跑坏有跑前快照）
  - 每天凌晨 3 点 ±20min：arXiv 采集管线（采集 → AI 过滤 → 打标 → GLM 抽取 → OpenAlex 补全 → 消歧 → 关系建立），跑完自动执行 C1–C10 数据不变量巡检
  - 每天凌晨 4 点 ±10min：AI 媒体 RSS 资讯采集 + 项目合作抽取（M2）
  - 每天凌晨 5 点 ±10min：高校官网定向爬取 + 学术传承抽取（M2）
  - 每 60 秒：failed_jobs 退避重试扫描（1/5/25min 指数退避，3 次后转死信）
  - 每天早上 8 点：死信巡检（记日志提醒；重跑走 `backend/scripts/retry_failed.py`）
- **流程**：获取 → 抽取 → 入库 → 更新关系

#### 2. 手动触发

- 在管理后台提供"立即更新"按钮（直接调用 APScheduler 的 job 函数）
- 实时显示更新进度
- 更新完成后刷新数据

## 环境变量配置

### GLM API 配置

```bash
# GLM API 配置（backend/.env，实际变量名以 .env.example 为准）
GLM_API_KEY=your_glm_api_key
GLM_MODEL=glm-5.3
GLM_BASE_URL=https://open.bigmodel.cn/api/anthropic
GLM_REQUEST_TIMEOUT_MS=120000
```

> 注意：`GLM_BASE_URL` 不带 `/v1/messages` 后缀（由 anthropic SDK 拼接完整路径）。
> 单次调用 max_tokens 按调用点分别设定（论文抽取 4000 / 网页抽取 16000 / 资讯抽取 2000），
> 无全局环境变量。

### 数据库配置

```bash
# PostgreSQL 配置
DATABASE_URL=postgresql://user:password@localhost:5432/prof_graph
POSTGRES_USER=your_user
POSTGRES_PASSWORD=your_password
POSTGRES_DB=prof_graph
```

### 服务配置

```bash
# 后端服务配置
PORT=8000
HOST=127.0.0.1

# 前端：Vite dev server 固定 5173，经 dev 代理以 /api 相对路径
# 访问后端（frontend/vite.config.ts），无需配置 API 地址变量
```

## 定时任务配置

> 定时任务由应用内的 **APScheduler** 管理（随 FastAPI 进程启动），不再依赖系统 cron 或 Windows 任务计划。详细配置见 [03-技术架构设计.md - 任务调度](./03-技术架构设计.md#任务调度apscheduler应用内调度)。

### 调度任务清单

| 任务 | 频率 | 说明 |
|------|------|------|
| 全库备份 | 每天凌晨 2 点 ±5min | pg_dump 自定义格式，滚动保留 7 份（`backend/backups/`） |
| arXiv 采集管线 | 每天凌晨 3 点 ±20min | 采集 → AI 过滤 → 打标 → GLM 抽取 → OpenAlex → 消歧 → 建关系，后跑 C1–C10 巡检 |
| RSS 资讯链 | 每天凌晨 4 点 ±10min | AI 媒体资讯采集 → 项目合作抽取（M2） |
| 官网爬取链 | 每天凌晨 5 点 ±10min | 高校种子定向爬取 → 学术传承抽取（M2） |
| 失败重试扫描 | 每 60 秒 | failed_jobs 按 1/5/25min 退避重试，3 次转死信 |
| 死信巡检 | 每天早上 8 点 | 记日志提醒；重跑走 `backend/scripts/retry_failed.py` |

> 潜在关系重算（common_network / research_similarity / spatiotemporal）属 M3 范围，尚未实现。

## 数据管理

### 数据备份

虽然系统不强制要求备份机制，但建议定期备份数据库：

```bash
# PostgreSQL 备份
pg_dump -U user -d prof_graph > backup_$(date +%Y%m%d).sql
```

### 数据恢复

每日备份为 pg_dump 自定义格式（压缩），用 pg_restore 恢复到**空库**：

```bash
"C:\tools\pg15\pgsql\bin\pg_restore.exe" -h 127.0.0.1 -U prof_graph -d <目标空库> \
  --no-owner --no-privileges "backend/backups/prof_graph_YYYYMMDD_HHMM.dump"
```

恢复后核对：逐表行数比对、`GET /api/admin/integrity` 应 `ok=true`、alembic_version 与代码迁移头一致。

## 合规与成本控制

### 合规处理

系统从公开渠道（arXiv、RSS、高校官网）采集个人信息建图谱，需注意合规：

| 合规项 | 处理方式 |
|--------|---------|
| **遵守 robots.txt** | 高校官网爬取前检查 robots.txt，禁止抓取的路径不爬 |
| **仅采集公开信息** | 不采集需要登录、付费、私密渠道才能获取的数据 |
| **遵守数据源 ToS** | 各数据源的服务条款，明确禁止抓取的源不接入 |
| **敏感字段加密** | 个人邮箱、电话等敏感字段在数据库中加密存储 |
| **删除接口** | 提供数据删除接口，支持按人员删除其所有关联数据 |

### GLM 成本熔断 ⭐

为避免 arXiv 某天大更新等原因导致 GLM 账单失控，设置成本熔断机制：

```python
# 双预算（backend/.env 可配；settings 默认值：日 120 万 / 周 600 万 tokens）
# TOKEN_BUDGET_DAILY / TOKEN_BUDGET_WEEKLY
# 分级动作：日 80% 告警 → 日 100% 停细筛 → 周触顶停抽取；
# 熔断后管理员可经 POST /api/admin/breaker/resume 手动放行（当日有效），次日/次周自动恢复

# 监控逻辑
async def check_budget_before_call():
    today_usage = get_today_token_usage()
    if today_usage >= DAILY_TOKEN_BUDGET:
        # 触发熔断：暂停抽取任务，发告警
        pause_extraction_jobs()
        send_alert(f"GLM 日成本熔断：今日已用 {today_usage} tokens")
        return False
    return True
```

| 熔断项 | 阈值（settings 默认，.env 可配） | 处理 |
|--------|-----------|------|
| 每日 token 上限 | 120 万 tokens | 80% 告警；100% 停细筛，次日自动恢复 |
| 每周 token 上限 | 600 万 tokens | 周触顶停抽取，次周自动恢复 |
| 单次任务失败率 | > 30% | 暂停任务并告警，避免连环失败浪费成本 |

> 开发期 `.env` 已临时放开为 5000 万/日、2 亿/周（M2-T16 D1 决议），上线前收紧回生产值。

## 常见问题

### Q1: GLM API 调用失败

**检查**：
1. API Key 是否正确配置
2. 网络连接是否正常
3. API 端点是否正确

### Q2: 数据库连接失败

**检查**：
1. PostgreSQL 服务是否运行
2. 数据库配置是否正确
3. 端口是否被占用

### Q3: 前端无法连接后端

**检查**：
1. 后端服务是否运行
2. API URL 是否正确
3. 端口是否正确
